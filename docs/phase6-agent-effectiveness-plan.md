# Phase 6: Gemini Agent Effectiveness Experiment

## Objective

Measure whether Continuum improves verified coding-agent outcomes and context
efficiency when used through the Antigravity CLI, while separating the effect
of Continuum from the effect of model choice.

## Experimental design

Use a paired 2 × 2 design:

| Model | Continuum off | Continuum on |
|---|---|---|
| Gemini 3.8 Flash Medium | baseline | treatment |
| Gemini 3.1 Pro Low | baseline | treatment |

The primary comparison is each model against itself with and without
Continuum. Comparing only one model with Continuum to another model without it
would confound the result and is not a valid Continuum effectiveness test.

Each cell runs the same task on a fresh repository copy, with the same prompt,
permissions, timeout, effort setting, initial repository snapshot, and
validation command. Run order is randomized. Use at least three repetitions
per cell for the pilot and five or more for the decision run.

## Treatment definitions

### Continuum off

Antigravity receives the task and has ordinary repository access. No Continuum
MCP server, precomputed packet, session recovery packet, or Continuum prompt
instructions are available.

### Continuum on

Antigravity receives the identical task and has the repository-scoped
Continuum MCP server. The prompt instructs it to use the plan, initial-context,
request-context, signal, and report operations when useful. The agent remains
responsible for deciding what to retrieve; Continuum must not inject hidden
solution content.

The MCP configuration must be isolated per benchmark run so one run cannot
leak tools, sessions, or cached state into another run.

## Task corpus

The frozen pilot task manifest is
`packages/context-engine/benchmarks/v1/phase6-tasks.json`. Start with these 12
tasks, balanced across difficulty and context shape:

- 3 local bug fixes requiring implementation plus tests
- 3 cross-package changes
- 2 database/schema or migration tasks
- 2 public API/contract changes
- 1 security-sensitive change
- 1 documentation/configuration mismatch

Tasks are drawn from the existing manually labelled benchmark fixtures and
fresh copies of the Continuum repository. Every task definition must include:

- exact base commit and repository fixture;
- natural-language task prompt;
- required files/symbols and required behavior;
- visible and hidden validation commands;
- expected allowed-modification paths;
- a manually authored rubric, written before runs;
- a deterministic task ID and input hash.

Do not score retrieval against labels generated by Continuum itself. Ground
truth is authored before execution and is kept separate from agent output.

## Primary success measures

The main outcome is `verified_task_success`:

1. the repository builds/typechecks;
2. all pre-existing tests still pass;
3. hidden task tests pass;
4. the patch satisfies the task rubric;
5. no forbidden or out-of-scope files were changed.

Report this as a binary result per run and aggregate success rate with paired
confidence intervals. A task is not successful merely because the agent
produced a plausible explanation or changed the expected file.

Secondary quality measures:

- hidden-test pass rate;
- regression count;
- patch correctness rubric score;
- scope violation count;
- number of repair/retry loops;
- time to verified success;
- clean completion rate versus timeout/failure.

## Efficiency and cost measures

Record raw evidence, not only percentages:

- provider input tokens;
- cached input tokens;
- output tokens;
- reasoning tokens, when supplied;
- tool-call count;
- compaction count and compaction tokens, when supplied;
- Continuum estimated context tokens;
- newly delivered, restored, referenced/repeated, and omitted context;
- wall-clock duration;
- derived provider cost and pricing-profile identity;
- cost per verified task;
- tokens per verified task.

Do not subtract Continuum's estimated tokens from provider input tokens and
call the difference savings. The valid primary efficiency comparison is the
observed provider cost/tokens and success rate between paired off/on runs.
Continuum estimates are explanatory diagnostics.

## Context-effectiveness measures

For treatment runs, additionally measure:

- required-context recall: required files/symbols present in delivered or
  referenced context;
- irrelevant-context precision at the packet boundary;
- first useful retrieval latency;
- number of progressive retrieval requests;
- duplicate-token avoidance estimate;
- recovery-packet reconstruction success after a forced restart test;
- context utility per delivered token;
- coverage completion before the first successful validation.

For both arms, measure agent exploration cost from the Antigravity event log:
files inspected, shell commands, failed test loops, and repeated reads. These
are outcome metrics, not substitutes for provider token telemetry.

## Fairness and reproducibility controls

- Fresh clone/copy for every run; never reuse a modified worktree.
- Same model version, effort, timeout, prompt, environment, and validation.
- Randomized task and arm order.
- No human intervention after launch.
- Record CLI version, model ID, OS, Node version, git base hash, task hash,
  Continuum version, MCP configuration hash, and timestamps.
- Preserve stdout/stderr, structured agent events, git diff, test output,
  Continuum session report, and final result in an append-only run directory.
- Redact secrets before storing artifacts.
- Treat provider rate limits and infrastructure failures as censored runs;
  rerun them under a documented policy instead of silently excluding them.

## Analysis rules

For every task and model, compare off versus on as paired observations. Report:

- absolute success-rate difference;
- relative success-rate difference only when the baseline is non-zero;
- median and p90 provider input/output/cached tokens;
- median and p90 cost per verified task;
- median time to verified success;
- context-retrieval and duplicate-avoidance distributions;
- 95% bootstrap confidence intervals;
- failure categories and representative traces.

The experiment is a positive result only if Continuum improves verified-task
success or reduces cost/tokens per verified task without a practically
important regression in correctness, scope safety, or completion time.

## Runner usage

Preview a run without using model quota:

    node scripts/phase6-agent-runner.mjs --task small-local-token-refresh --model gemini-3.8-flash-medium --treatment continuum_off

Execute only after the runner and treatment configuration are verified:

    node scripts/phase6-agent-runner.mjs --execute --keep --task small-local-token-refresh --model gemini-3.8-flash-medium --treatment continuum_off

The current runner intentionally reports validation as `not_configured` until
P6-06 adds task-specific visible/hidden verification. Its output must not be
called a successful benchmark result yet.

The first preliminary smoke is recorded in
`packages/context-engine/benchmarks/v1/phase6-smoke-results.json`. Both arms
reached the Antigravity five-minute print timeout; the Continuum-on arm used
MCP and produced the expected patch, while the off arm produced no patch. This
is runner/MCP wiring evidence only, not an effectiveness conclusion.

The first matched 15-minute pair is recorded in
`packages/context-engine/benchmarks/v1/phase6-long-smoke-results.json`. Both
conditions independently passed all six available fixture tests. In this pair,
Continuum-on used 33.2% more reported total tokens and 68.2% more tool calls,
while finishing 2.6% faster and reducing output/thinking tokens. This remains
one pair, without dollar pricing or hidden verification, so it is not a final
effectiveness result.

After restricting the MCP surface and requiring one-shot initial context, the
compact treatment reduced reported total tokens by 18.8% and duration by 27.3%
against that control, with all six fixture tests independently passing. This
single-pair result is recorded in
`packages/context-engine/benchmarks/v1/phase6-compact-smoke-results.json` and
is a reason to continue with repetitions, not a final claim.

## Preliminary four-cell pilot repetition (2026-09-13)

The first complete repetition across Gemini 3.8 Flash Medium and Gemini 3.1
Pro Low is recorded in `docs/phase6-pilot-results-2026-09-13.json`. Compact
Continuum reduced total reported tokens by 24.48% for Gemini 3.1 Pro Low, but
increased them by 8.72% for Gemini 3.8 Flash Medium. It reduced duration for
both models by 46.66% and 32.76%, respectively. The Gemini 3.1 control did
not produce a patch, while its compact counterpart did; Gemini 3.8 produced a
patch in both arms. These correctness observations are not success-rate
evidence until P6-06 independently verifies the task and checks patch scope.

The recovery smoke is available as `pnpm test:phase6-recovery`. It exercises
initial delivery, explicit context expansion, a test-failure signal, and
persisted recovery reconstruction; the current fixture passed with three
deliveries, two signals, and a 4,728-byte recovery packet.
